# HomeDishPicker 项目总结

## 1. 项目成果

HomeDishPicker 是一个网页版家常菜随机抽签系统。它从一个简单的“今天吃什么”想法，逐步迭代成了一个可以在电脑和手机浏览器中使用的小型前端应用。

当前系统已经具备：

- 从“我会做的菜”中随机抽签。
- 抽签时显示滚动定格效果。
- 根据冰箱食材筛选可做菜品。
- 展示当前食材可以参考制作的菜品。
- 管理常用食材标签。
- 添加、编辑、删除自定义菜品。
- 按分类折叠展示抽签库。
- 重命名抽签库分类。
- 随机发现抽签库以外的新菜。
- 将新菜加入自己的抽签库。
- 为菜品提供小红书教程入口。
- 导出、导入和重置本地数据。
- 使用 Git 管理版本，并上传到 GitHub。
- 使用 GitHub Pages 发布为可访问的网址。

这个项目的价值不只是完成了一个网页工具，更重要的是完整练习了“从想法到上线”的流程。

## 2. 学到的核心技能

### 前端基础

本项目使用了纯 HTML、CSS 和 JavaScript，没有引入框架。

练习到的内容包括：

- 使用 `index.html` 搭建页面结构。
- 使用语义化标签组织标题、表单、按钮、列表和区域。
- 使用 `css/style.css` 控制页面布局、响应式效果、按钮状态和卡片样式。
- 使用 `js/app.js` 编写交互逻辑。
- 使用 DOM API 获取页面元素、监听点击和输入事件。
- 使用数组、对象、函数、条件判断和循环处理业务数据。
- 使用 `localStorage` 在浏览器中保存用户数据。
- 使用 `FileReader` 读取导入的 JSON 文件。
- 使用 `Blob` 和下载链接导出 JSON 文件。
- 使用 `setInterval` 和 `setTimeout` 实现抽签滚动动画。
- 使用 URL Scheme 尝试打开手机 App。

### Git 和版本控制

这个项目完整练习了 Git 的基本工作流：

- `git status` 查看当前状态。
- `git add` 暂存文件。
- `git commit -m` 保存一个版本。
- `git log --oneline` 查看提交历史。
- `git remote add origin` 连接 GitHub 仓库。
- `git push` 推送代码到 GitHub。

也练习了如何拆分 commit：

- 初始化项目文件。
- 添加 README。
- 添加页面结构。
- 添加样式。
- 实现抽签逻辑。
- 增加食材推荐。
- 增加新菜灵感。
- 完善 README。
- 增加 GitHub Pages 部署说明。
- 迭代常用食材、分类管理、小红书跳转等功能。

一个重要经验是：每个 commit 尽量只解决一个清晰问题。这样以后回看历史时，可以知道每个版本为什么改、改了什么。

### README 和项目文档

README 不只是说明书，也是项目管理工具。

本项目中的 README 包含：

- 项目目标。
- 当前功能。
- 技术栈。
- 项目结构。
- 如何运行。
- 如何使用。
- 数据保存说明。
- Git commit 划分建议。
- 版本记录。
- 后续计划。
- GitHub Pages 部署步骤。
- 当前限制。

通过持续更新 README，可以让项目始终保持清晰：现在做到哪一步、还有什么没做、下一步要做什么。

### GitHub 和部署

本项目已经上传到 GitHub，并可以通过 GitHub Pages 发布为网页。

练习到的知识包括：

- 在 GitHub 创建远程仓库。
- 将本地仓库推送到 GitHub。
- 在 GitHub 上查看 commit 历史。
- 使用 GitHub Pages 发布静态网页。
- 理解线上网页更新流程：本地修改、commit、push、等待 Pages 自动部署。

这说明一个纯静态网页项目可以不需要服务器，也能变成手机可访问的产品。

## 3. 学到的专业知识

### 需求拆解

一开始的需求很简单：随机抽一道家常菜。

后续逐步拆成更具体的问题：

- 用户不知道吃什么，需要随机结果。
- 用户冰箱里有食材，希望推荐能做的菜。
- 用户会做的菜会变化，需要可维护的抽签库。
- 用户想尝试新菜，需要抽签库以外的灵感。
- 用户想看教程，需要跳转到外部平台。
- 用户手机使用，需要部署到线上。
- 用户数据要保留，需要本地存储和导入导出。

这说明做项目时，不要一开始就追求“大而全”。更好的方法是先完成最小可用版本，再根据真实使用场景迭代。

### 数据建模

项目中的菜品不只是一个字符串，而逐渐变成结构化数据：

```js
{
  name: "番茄炒蛋",
  ingredients: ["番茄", "鸡蛋"],
  category: "快手下饭",
  status: "常吃",
  tutorialUrl: "",
  note: "经典快手菜"
}
```

这就是数据建模：把现实中的“菜”拆成程序可以处理的字段。

有了结构化数据，系统才能支持：

- 按食材匹配。
- 按分类折叠。
- 按状态筛选。
- 保存备注。
- 打开教程。
- 导出和导入。

### 状态管理

虽然项目没有使用 React 或 Vue，但仍然有状态管理。

例如：

- `dishes`：当前抽签库。
- `fridgeIngredients`：当前冰箱食材。
- `quickIngredients`：常用食材标签。
- `drawHistory`：抽签历史。
- `categoryRenames`：分类重命名记录。
- `lastNewDish`：最近随机到的新菜。

页面显示会随着这些状态变化而变化。理解这一点，对以后学习前端框架很有帮助。

### 本地存储

项目使用 `localStorage` 保存数据。

优点：

- 不需要后端。
- 刷新页面后数据还在。
- 适合练习项目和小工具。

限制：

- 数据只保存在当前浏览器。
- 换手机或换浏览器不会自动同步。
- 清理浏览器数据可能丢失。

因此项目又增加了导入导出 JSON，用来备份和迁移数据。

### 外部 App 跳转

项目中小红书教程入口经历了两个阶段：

- 先跳转到小红书网页版搜索。
- 再尝试使用 `xhsdiscover://` 打开小红书 App。

这里学到一个实际开发限制：网页不能完全控制手机系统和第三方 App。尤其是在微信内置浏览器中，第三方 App 跳转可能会被拦截。因此系统需要兜底方案：打不开 App 时回退到网页搜索。

### 产品取舍

有些功能理论上可以做，但不适合当前阶段直接做。

例如：

- 实时从小红书抓取菜谱。
- 自动识别未知菜品需要哪些食材。
- 多设备同步数据。
- 用户登录和云端数据库。

这些功能需要后端、接口权限、账号系统或 AI 服务。当前项目选择了更稳妥的方案：内置新菜灵感池、小红书搜索链接、本地存储。这是很重要的产品判断。

## 4. 一个独立项目的完整流程

以后做新的独立项目，可以按这个流程推进。

### 第一步：定义目标

先用一句话说明项目要解决什么问题。

例如：

```text
制作一个网页版家常菜随机抽签系统，帮助用户快速决定今天吃什么。
```

这一句话要足够清楚，让别人一看就知道项目的价值。

### 第二步：确定第一版范围

第一版不要做太大，只做最小可用功能。

本项目第一版是：

- 页面能打开。
- 有候选菜列表。
- 点击按钮能随机抽一道菜。
- 能显示结果。

第一版的目标是跑通，不是完美。

### 第三步：设计文件结构

简单项目也要有清晰结构。

本项目结构是：

```text
HomeDishPicker/
├── index.html
├── css/
│   └── style.css
├── js/
│   └── app.js
├── README.md
└── .gitignore
```

这样做的好处是职责明确：HTML 管结构，CSS 管样式，JS 管逻辑，README 管说明。

### 第四步：实现基础功能

先让项目真正能用。

不要一开始就纠结复杂功能。只要用户可以完成核心动作，就可以进入下一步。

### 第五步：用 Git 保存版本

每完成一个小目标，就提交一次。

推荐格式：

```text
feat: add random dish picker
style: add page layout
docs: update README
```

这样以后查看历史时，能清楚看到项目是怎么长出来的。

### 第六步：持续更新 README

README 应该随着项目一起成长。

每次新增功能后，至少更新：

- 当前版本。
- 使用方法。
- 版本记录。
- 后续计划。
- 当前限制。

好的 README 会让项目更像一个真正的作品。

### 第七步：部署到线上

当本地能运行后，就应该考虑部署。

纯静态网页可以用 GitHub Pages：

1. 创建 GitHub 仓库。
2. 推送代码。
3. 开启 Pages。
4. 得到线上网址。
5. 用手机测试。

部署之后，项目从“本地文件”变成了“别人可以访问的网页”。

### 第八步：真实使用并收集问题

真正使用后，才会发现新需求。

本项目就是这样逐步发现：

- 手机要能打开。
- 小红书教程要尽量跳 App。
- 新菜不能和抽签库重复。
- 常用食材要能自定义。
- 分类名称要能修改。
- 输入食材后要看到所有可做菜品。

真实使用会推动项目变得更合理。

### 第九步：迭代而不是重做

每次新需求都不需要推翻重来。

更好的方式是：

- 看现有代码。
- 找到相关模块。
- 小范围修改。
- 更新 README。
- commit。
- push。
- 在线验证。

这就是项目迭代能力。

## 6. 下一阶段建议

这个项目目前已经基本完成核心需求。后续如果继续做，建议从下面几个方向选择一个，不要同时做太多：

- 优化手机端 UI，让它更像一个真正的小工具。
- 增加菜品图片，让结果更直观。
- 增加“今天不想吃什么”的排除功能。
- 增加按耗时筛选，例如 10 分钟、30 分钟、周末慢慢做。
- 增加 GitHub Pages 线上地址到 README。
- 学习如何把项目升级为 Vite 或 React 项目。
- 学习如何接入后端，实现多设备同步。

当前最重要的收获是：你已经完整走过了一次从想法、规划、开发、版本控制、部署、手机验证到持续迭代的流程。
